# BB-70: пустая тестовая база

Baseline `supabase/migrations/20260929000000_bb70_database_baseline.sql`
предназначен только для новой пустой базы. Это реконструкция DDL по сохранённым
метаданным `tests/bb24/schema.sql` и контрактам серверных репозиториев, без чтения
реальной Supabase. Снимок BB-24 остаётся историческим тестовым fixture.

Baseline создаёт только `users`, `masters`, `services`, `slots`, `bookings`.
Telegram ID — обычные bigint PK; три внутренних ID — bigint identity BY DEFAULT.
Сохранены nullable FK с ON DELETE CASCADE, nullable статусы и старые defaults
`available` / `confirmed`. Серверные RPC явно записывают рабочие русские статусы;
менять исторические defaults для этого не требуется. Адреса, аватар, город,
описание слота и reason добавляет следующая миграция. Таблица webhook и все RPC
создаются своими последующими миграциями.

Baseline не создаёт роли, `auth` или `storage`. Они должны существовать в
полноценной Supabase до применения пользовательских миграций. Включён RLS без
политик, отозваны клиентские grants на пять таблиц и три identity sequence,
`service_role` получает schema USAGE, CRUD и sequence USAGE. BB-01 проверяет
наличие BYPASSRLS у платформенной роли и сохраняет эти права. Клиентских grants
и глобальных изменений default privileges baseline не вводит.

Исторические результаты ниже относятся к первоначальным десяти миграциям.
Текущие тесты применяют также BB-73 и требуют сохранения отменённых записей
при отказе удаления слота. BB-70 по-прежнему предназначена только для пустой базы.

`20260930_bb.sql` нестандартен по длине, но совместим с проверенным правилом
CLI `^([0-9]+)_(.*)\.sql$`: длина версии не фиксирована. Источники:
[CLI v2.54.11 file.go](https://github.com/supabase/cli/blob/v2.54.11/pkg/migration/file.go),
[list.go](https://github.com/supabase/cli/blob/v2.54.11/pkg/migration/list.go),
[проверенный исходник нового CLI](https://github.com/supabase/cli/blob/e365ad6b96a2ba4327b9220ecba5e4504e5fbecc/apps/cli/src/command-internal/migration-list.ts).
CLI сортирует имена лексикографически; baseline идёт первым. Все версии уникальны.
Поэтому старое имя и SQL сохранены: оснований менять идентификатор истории нет.
Это проверка исходного правила, а не запуск CLI.

## Отдельный seed

`supabase/seeds/test_catalog.sql` содержит три услуги с префиксом `[ТЕСТ BB-70]`.
Это отдельный opt-in SQL после миграций, не production-миграция и не автоматически
подключённый seed. Он рассчитан на однократное применение к пустому каталогу;
повторное применение добавит ещё три строки. ID генерируются sequence, поэтому
следующие вставки сервера не конфликтуют. Формат — только реальные поля
`service_id,name,description`; `icon_url` и `duration` каталог добавляет как null
на уровне API. Пользователей, мастеров и слотов seed не создаёт. Города появляются
в каталоге после создания слотов через форму мастера.

## Локальная проверка

Нужны имеющиеся PostgreSQL binaries (`initdb`, `pg_ctl`, `psql`) и pytest.
Никаких DSN, `.env`, Supabase SDK или облачных запросов тесты не используют.
Кластер создаётся в pytest basetemp, слушает только Unix socket и останавливается
в finally. Каждая база создаётся пустой, затем удаляется; схема BB-24 не загружается.

```sh
python3 -m pytest tests/bb70 -q --tb=short -p no:cacheprovider --basetemp=/private/tmp/bb70-pytest
python3 -m pytest tests/bb63 tests/bb64 tests/bb66 tests/bb67 -q --tb=short -p no:cacheprovider --basetemp=/private/tmp/bb70-regression
```

Результат 2026-11-02: BB-70 — **7 passed**; BB-63/64/66/67 — **124 passed**.
Оба набора выполнены на одноразовых кластерах PostgreSQL 18.4. В ограниченном
sandbox `initdb` не стартовал; успешные прогоны выполнены с разрешением запуска
локальных процессов за пределами sandbox.

Новый набор: 7 проверок, включая шесть независимых созданий пустой базы, два
режима ACL (обычные и широкие platform-like defaults), точную структуру колонок,
PK/FK, CASCADE, индексы, 10 RPC, права таблиц/колонок/sequences/functions,
регистрацию без перезаписи профиля, каталог, создание слота, бронирование,
подтверждение/отклонение, отмену моделью/мастером, удаление и webhook receipt RPC.
Проверяется SQL-контракт репозиториев; HTTP Edge Functions/PostgREST не запускаются.
BB-63 теперь тоже загружает baseline вместо старого снимка; его fixture используют
регрессионные BB-64/66/67. Исторический BB-24 integration test пропускает новый
baseline, поскольку уже загрузил снимок. Для BB-24 нужны отдельные зависимости
`pgserver` и `psycopg`; в этом окружении их нет, этот набор не запускался.

`storage_fixture.sql` отдельно создаёт минимальные метаданные Storage для обычного
PostgreSQL. Проверяются настройки bucket и SQL-политики BB-03, в том числе
блокировка записей при дополнительной широкой разрешающей политике. Это НЕ
проверка настоящего Storage, MIME-декодирования, загрузки или выдачи публичных URL.
Fixture никогда не копируется в `supabase/migrations`.

## Что ещё нужно перед тестовым развёртыванием

Supabase CLI и полноценный локальный стек здесь недоступны; проверено обычным
PostgreSQL 18.4 (Homebrew). Тяжёлые зависимости не устанавливались. Следующий
этап — в отдельном одноразовом рабочем каталоге инициализировать локальный CLI
проект, перенести только реальные миграции, проверить команды через `--help`,
запустить локальный стек и выполнить `migration list --local` и `db reset --local`.
Нужны два чистых прогона со штатными платформенными схемами/ACL и opt-in seed,
проверка реального Storage API и PostgREST FK embedding. Полный сценарий приложения
потребует конфигурации локальных Edge Functions, серверных ключей и тестового
Telegram initData; секреты не добавлять в Git или клиентскую сборку.

Никакие облачные проекты, production, существующие базы, deploy, PR или merge
в рамках BB-70 не затрагиваются. Добавленный baseline нельзя воспроизводить
поверх непустой базы или применять к ранее развёрнутой истории без отдельного
плана согласования миграций.
