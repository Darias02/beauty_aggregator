# Подготовить фотографии слотов к публикации

Локальный MVP использует закрытый bucket `slot-photos`. Миграция подготовлена, к удалённой базе не применялась. Публикация требует отдельного разрешения.

## Проверить локально

Запустите проверки из корня репозитория:

```sh
deno task --config supabase/functions/slot-photos/deno.json check
deno task --config supabase/functions/slot-photos/deno.json lint
deno task --config supabase/functions/slot-photos/deno.json test
python3 -m pytest tests/bb63 tests/bb70 tests/slot_photos -q
python3 -m pytest tests/bb75 -q
```

PostgreSQL-тесты создают временный кластер с отдельной Storage metadata fixture. Они не обращаются к удалённым базам. Браузерные тесты используют mock API и блокируют внешнюю сеть. Эти проверки не заменяют тест настоящего Storage.

## Подготовить тестовую среду

1. Проверьте миграцию `supabase/migrations/20261118141559_slot_work_photos.sql`. Она создаёт таблицу `slot_photos`, серверные RPC и закрытый bucket с лимитом 2 МБ на объект. Клиентские роли не имеют доступа к таблице, RPC или объектам bucket.
2. После согласования примените миграцию к отдельной тестовой базе. Не запускайте её повторно и не применяйте вместо уже выпущенной другой миграции с таким же номером.
3. Выпустите функцию `slot-photos` с WASM-файлом, указанным в `supabase/config.toml`. Используются существующие pinned-версии Supabase JS и ImageMagick. Bucket `master-avatars` не меняется.
4. Настройте серверные `BOT_TOKEN`, `SUPABASE_URL` и секретный ключ через принятый в проекте способ. Ключ не должен попадать в frontend, скриншоты или логи.
5. Выпустите frontend после миграции и функции. Существующие `slots-read` и `slots-write` остаются без изменений.
6. Проверьте загрузку, подпись URL, истечение ссылки, чужого владельца, архивную запись и очистку на настоящем тестовом Storage.
7. Проверьте Telegram на физических iPhone и Android. Используйте JPEG с EXIF, PNG, WebP и HEIC, медленную сеть, отключение сети и повторный вход в приложение.

## Проверить поведение MVP

Форма принимает максимум 3 необязательных фото. Исходный файл ограничен 25 МБ. Браузер уменьшает снимок до 1600 px и JPEG до 700 КБ, после чего отправляет файл через сервер. JPEG, PNG и WebP поддерживаются. HEIC и HEIF отклоняются с предложением экспортировать JPEG. Автоматическое преобразование HEIC в MVP не входит.

Сначала существующий API сохраняет слот. Затем отдельные запросы загружают фото. При сбое форма показывает номер сохранённого слота и кнопку повторной загрузки. Повторное создание слота не выполняется. Мастер может продолжить с уже сохранёнными фото или управлять фотографиями через свои записи. Незавершённые загрузки видны только владельцу и могут быть удалены. Несохранённые файлы находятся в памяти страницы, после перезагрузки их нужно выбрать заново.

Сервер проверяет подпись и срок действия Telegram initData. SQL проверяет владельца под блокировкой слота и выделяет одну из трёх позиций. Клиент передаёт UUID операции, сервер формирует путь из проверенного владельца, слота и UUID. Имя исходного файла не используется, перезапись объекта запрещена. Повтор операции использует прежний UUID.

Сервер проверяет сигнатуру, MIME, полный растр, пределы разрешения и размера. Затем применяет EXIF orientation, уменьшает изображение при необходимости и повторно кодирует JPEG без метаданных. Анимация запрещена. В поиске показывается одно компактное превью. Раскрытая карточка показывает все фото. Просмотр открывается в диалоге с закрытием и Escape. Нижняя навигация не меняется.

Авторизованная зарегистрированная модель получает фотографии доступных слотов. Владелец и участник соответствующей записи сохраняют доступ к фотографиям недоступного или архивного слота. Посторонний пользователь не получает ссылок. Прямой загрузки из браузера в Storage нет.

Ссылки действуют 1 час. Frontend обновляет их перед истечением, при возвращении приложения на передний план и при ошибке загрузки изображения. Подписанные URL не сохраняются в БД или localStorage. Уже выданная ссылка доступна её получателю до истечения срока; это не механизм мгновенного отзыва.

## Удалить неиспользуемые файлы

Передайте серверные переменные окружения явно. Скрипт не читает `.env` и не выводит пути или ключи.

Сначала выполните просмотр без изменений:

```sh
deno run --config supabase/functions/slot-photos/deno.json \
  --allow-env --allow-net tools/cleanup_slot_photos.ts
```

Для согласованной среды добавьте `--apply`:

```sh
deno run --config supabase/functions/slot-photos/deno.json \
  --allow-env --allow-net tools/cleanup_slot_photos.ts --apply
```

Команда обрабатывает до 500 записей за запуск. Повторяйте её, если остались кандидаты. Для эксплуатации достаточно ежедневного запуска существующим планировщиком или оператором; отдельный сервис не требуется.

SQL сначала помечает записи `deleting`, чтобы поздняя загрузка не могла стать доступной. Затем скрипт удаляет объекты через Storage API. Готовые фотографии существующих слотов не попадают в очистку. Незавершённые загрузки считаются устаревшими через 24 часа. При удалении слота остаётся запись с путём для последующей очистки.

При ошибке удаления запись сохраняется для следующего запуска. После успеха записывается время очистки. Небольшие записи `deleting` сохраняются и повторно проверяются раз в сутки, чтобы убрать объект даже при крайне позднем завершении запроса загрузки. Автоматическое удаление этих служебных записей в MVP не реализовано; их накопление нужно учитывать при дальнейшем развитии. Если скрипт не запускать, неиспользуемые приватные файлы останутся в Storage.

## Ограничения перед выпуском

Настоящий Storage E2E локально не проверен: Docker daemon недоступен. Синтетический JPEG с EXIF проверяет ориентацию и удаление метаданных, но не заменяет тест медиатеки iPhone. Снимки интерфейса используют синтетические цветовые образцы.

На каждый отображаемый слот выполняется отдельный запрос списка фотографий. Отдельные миниатюры в Storage не создаются; компактное превью использует уменьшенный JPEG. При росте выдачи стоит добавить пакетное получение ссылок и отдельные миниатюры. Текущие ограничения сдерживают размер загрузки без новой инфраструктуры.

## Сохранить и перейти к тестовому запуску

Фотографии и редизайн формы подготовлены в ветке `codex/beauty-booking-ui`. Предыдущая интеграция DaData сохранена в родительском коммите `cdb3a6c` с сообщением `add address suggestions`. Форма сохраняет автодополнение города и адреса, ручной ввод, календарь и прежнюю логику создания слота. Заголовок, кнопка «Назад», подписи над полноширинными полями, многострочное описание, выбор фотографий и кнопка публикации присутствуют.

Проверка автодеплоя не подтвердила безопасность push в `develop`: действующей конфигурации в репозитории нет, а чтение настроек Vercel завершилось HTTP 403. Push не выполняется. Необходимо сначала проверить production branch, Git integration, ветки Preview и подключённые backend-ресурсы. Один только push в ветку с названием `develop` не доказывает изоляцию production.

Для перехода к настоящему Telegram выполните следующие шаги после отдельного разрешения владельца:

1. Выберите отдельные тестовые Supabase, Telegram-бот и frontend-проект. Подтвердите отсутствие связей с production.
2. Согласуйте и примените миграцию. Она одновременно создаёт таблицу, RPC, закрытый bucket `slot-photos` и политики доступа. Проверьте состояние bucket и лимиты.
3. Выпустите Edge Function `slot-photos` вместе с WASM. Проверьте наличие серверной конфигурации без вывода её значений. Изменение secrets требует отдельного разрешения.
4. Соберите frontend для тестового окружения и опубликуйте его. Настройте тестовый Mini App URL. Публикация frontend и изменение URL бота требуют разрешения.
5. Согласуйте ежедневный запуск `tools/cleanup_slot_photos.ts --apply` только в тестовой среде. Настройка планировщика и первое реальное удаление файлов требуют разрешения.
6. Проверьте в Telegram на iPhone и Android фотографии из медиатеки, HEIC-ошибку, повтор после сбоя, доступ чужого пользователя, архивные записи, обновление ссылок и очистку.

Миграция, удалённый bucket, Edge Function, frontend, настройки бота, secrets и очистка в этой подготовке не запускались и не менялись. Production остаётся вне разрешённого объёма работ.

Перед локальным сохранением проверки повторены: 68 UI-тестов BB прошли, 1 штатно пропущен; 13 UI-тестов DaData прошли; 34 теста PostgreSQL и 47 тестов API фотографий, слотов и DaData прошли. Typecheck, lint и `git diff --check` прошли. Проверены 13 уникальных номеров миграций. Поиск известных форматов секретных ключей в 43 файлах изменений и DaData не обнаружил совпадений. В тестовой заглушке DaData добавлено распознавание JSON-запросов, чтобы multipart-запросы фотографий не ломали подготовку UI-тестов.
